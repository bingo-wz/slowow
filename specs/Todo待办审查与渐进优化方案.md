# 慢慢：Todo 待办审查与渐进优化方案

审查日期：2026-11-16。代码基线：`e4e7297`。本文为建议稿，不表示待确认的交互或新增字段已经获得确认。

审查依据为用户提供的《Todo App 设计与交互优化指南》、已有需求与截图，以及当前 Android、数据库、同步和提醒代码。本轮不修改业务代码，不更新安装包；静态代码风险不等同于已在用户手机上发生的故障。

本轮强制重新执行了现有 JVM 单元测试：19 项通过，0 失败、0 跳过。未执行新的完整 UI、TalkBack 或小米真机验收，下面的验收表为待实施和补测内容。

## A. 现状总结

### 用户与使用情境

使用者是小学语文老师兼班主任，常在课间、走动、接收学校通知时短暂使用手机。核心链路是想到事情后快速记下、当天看见、完成后能确认、到时间能找回具体事项。目标设备为小米 12S，系统字体较大；具体系统版本和每日任务量尚待补充。

“慢慢”同时承担班级记录工作，保留已确认的“今天 / 记录”两个一级入口。今天只显示当天待办，其他日期在全部待办查看；日期组内拖动，跨日期通过编辑改期。这些规则不因通用 Todo 指南建议四个 Tab 或跨日期拖动而自动改变。

### 已有能力与适合保留的部分

- Kotlin、Jetpack Compose、Material 3、Room、WorkManager；已有 `Reorderable 3.1.0`，不需要另换拖动库。
- `TodayScreen` 作为首页，日期、菜单、学校通知和设置位于顶栏。
- `TaskAgenda` 使用 `LazyColumn` 和稳定任务 ID；复选框、完成划线、按日期折叠、同日拖动已具备。
- `TaskEditorScreen` 已允许仅标题保存，区分仅日期、日期时间、提醒时间，保留学校通知关联；返回已有未保存确认。
- `ClassRepository` 先保存本机，`SyncWorker` 负责后台同步；`LocalRecord` 已保存删除标记、操作 ID、服务端版本和冲突副本。
- `SyncEngine` 已有重试与冲突保留；登录凭证恢复首先读取本机，不能据此认定启动必须等待网络。
- 统一的字体、字号、圆角、图标描述、Tooltip、深浅色与系统触感已有实现，不需要重写主题。

任务模型现有字段为 `id/title/noticeId/dueAt/remindAt/done/createdAt/dueDate/sortOrder`。本轮不把指南中的备注、清单、标签、重复、子任务和任务优先级描述成既有能力，也不默认全部加入。

## B. 最重要的 5 个问题

P0 表示涉及内容保护或误操作恢复、应优先处理；P1 表示高频效率、可发现性或操作闭环问题；P2 表示需真实需求验证的增强能力。

### T01 · P0：旧编辑表单可能覆盖已经更新的任务

- **页面与代码**：`TaskEditorScreen` 的标题和时间按任务 ID 初始化并保留；`ClassRepository.saveTask` 直接回写整条任务，未比较打开编辑页时的记录快照。`RecordDao.saveLocal` 沿用保存时数据库中的服务端版本。任务详情的完成按钮也走整条 `saveTask`，列表完成则走事务化的 `setTaskDone`。
- **具体影响**：编辑期间，如果同步先把另一个版本写入本机，旧表单再次保存可能携带最新服务端版本覆盖新内容，绕过通常的服务端版本冲突检测。远端删除导致编辑对象消失时，也缺少专门的草稿保护和说明。这是由代码路径推导的风险，本轮未复现真实账号事故。
- **推荐修改**：编辑开始时捕获基线；保存时在同一事务中比较当前内容、删除状态和基线。仅合并用户真正修改的字段，碰到同字段变更时展示两版供选择。详情完成按钮复用已有 `setTaskDone`，其他字段不随完成动作回写。
- **原因**：同步层冲突处理不能代替“编辑开始到保存”之间的内容校验；完成动作只应改变完成状态。
- **结构和流程影响**：首步不需要增加 `WorkTask` 字段或修改服务端协议；需要给现有编辑保存链路传递基线，并补充冲突与记录已删除的分支。比较应区分内容变化和纯同步确认，避免把服务端确认也误报为内容冲突。
- **证据**：[编辑与保存](../android/app/src/main/java/app/manman/teacher/ui/WorkScreens.kt)、[任务写入](../android/app/src/main/java/app/manman/teacher/data/ClassRepository.kt)、[版本与回写](../android/app/src/main/java/app/manman/teacher/data/LocalDatabase.kt)。

### T02 · P0：已有软删除，但用户没有撤销与恢复入口

- **页面与代码**：详情页已有删除确认，删除写入 `deleted=true`，反馈为“待办已删除”。`ManmanApp` 的 Snackbar 只有文字，没有操作按钮。列表内完成可以取消，但改期、排序、删除缺少统一撤销入口。
- **具体影响**：用户即使马上意识到误删，也无法自行找回任务；改错日期后需要先找到任务再修改。数据库还保留删除记录，不应描述为“已经物理永久清除”。
- **推荐修改**：先提供删除、改期和排序的短时撤销；复用现有 `SnackbarHost` 显示带“撤销”的反馈，时长遵循系统无障碍超时。撤销以同一任务 ID 写入新的操作，并核验最新记录，恢复受影响字段及原排序；发生新冲突时提示核对。
- **原因**：删除确认负责防止误触，撤销负责恢复已经发生的误操作，两者作用不同。已同步的删除仍应能通过新恢复操作处理。
- **结构和流程影响**：基础撤销可复用现有 tombstone、操作 ID 和版本机制，不要求改 Room 表；需要增加可执行的反馈事件及恢复操作。“最近删除”的保留期限与跨重启恢复属于后续产品规则，不能由 Snackbar 超时直接触发物理清理。
- **证据**：[删除与反馈](../android/app/src/main/java/app/manman/teacher/ui/WorkScreens.kt)、[Snackbar](../android/app/src/main/java/app/manman/teacher/ui/ManmanApp.kt)、[删除写入](../android/app/src/main/java/app/manman/teacher/data/ClassRepository.kt)。

### T03 · P1：快速记录仍需多次定位，输入中断后的草稿能力不足

- **页面与代码**：今天的加号放在 `TaskAgenda` 的普通列表头，向下滚动会离开屏幕；全部待办的顶栏加号则保持可见。新建进入完整编辑页，没有自动聚焦或键盘提交保存；日期和提醒区从一开始就全部展示。返回有明确的放弃确认，但没有独立草稿存储。
- **具体影响**：课间记录一件事需要找入口、点输入框、判断可选设置，再保存；被分享内容或导航打断后难以续写。不能把现有 `rememberSaveable` 等同于所有返回、强制停止或冷启动下的持久草稿。
- **推荐修改**：把今天的列表标题与唯一加号固定；先精简现有全屏编辑页，标题自动聚焦，提供键盘完成保存。日期以 Chip 明示，提醒按需展开。新增页的保存目标可见；保存后定位到任务。对未提交内容明确区分继续编辑、保留草稿和放弃。
- **原因**：首轮只缩短已有流程，比同时新增复杂面板、自然语言和多种入口更易验证，也更适合大字号。
- **结构和流程影响**：固定入口、聚焦、键盘提交和渐进显示不改变任务字段。页面暂存可先使用 Compose 状态保存；如果要求强制停止后仍恢复草稿，需要按账号隔离的本地持久草稿存储。新增草稿表时必须编写 Room 迁移，草稿不进入正式提醒和同步队列。
- **证据**：[今天列表头](../android/app/src/main/java/app/manman/teacher/ui/TodayScreen.kt)、[任务编辑页](../android/app/src/main/java/app/manman/teacher/ui/WorkScreens.kt)、[文本框](../android/app/src/main/java/app/manman/teacher/ui/LoginScreen.kt)。

### T04 · P1：任务保存后的位置与今天的统计口径不够清晰

- **页面与代码**：今日数量统计包含已完成项。全部待办按日期从早到晚展开，未安排日期放在最后。从今天创建默认今天；从全部待办或通知手动创建不自动填日期。
- **具体影响**：完成任务后“今日待办”数量不减；旧任务越积越多，今天、未来和未安排越难找到。无日期任务保存成功后不会出现在今天，用户可能误以为记录丢失。
- **推荐修改**：统计明确显示待处理数。已完成项先原位勾选划线，是否默认收起单独确认。全部待办增加轻量时间范围与状态筛选、未安排快捷入口，默认定位今天；保存后展示去向，必要时提供“查看”。
- **原因**：让用户能预测任务会出现在哪里，比增加更多统计和颜色更有效。继续遵守今天只显示当天任务，不自动顺延过期事项。
- **结构和流程影响**：筛选和计数复用现有日期、完成和排序字段，无需创建四个一级页面或新增 inbox 状态。若今后要区分计划执行日与截止时间，才需要独立讨论字段扩展。
- **证据**：[今日统计](../android/app/src/main/java/app/manman/teacher/ui/TodayScreen.kt)、[日期分组](../android/app/src/main/java/app/manman/teacher/ui/TaskAgenda.kt)、[新增默认日期](../android/app/src/main/java/app/manman/teacher/ui/ManmanApp.kt)。

### T05 · P1：提醒缺少“提醒的是谁、点开去哪里”的闭环

- **页面与代码**：`ReminderScheduler` 发送统一的课程或待办提醒，使用同一个通知 ID，打开应用的 Intent 没有任务目标。权限状态与设置入口已在设置页提供，但任务编辑页选择提醒时未关联展示权限状态。
- **具体影响**：老师收到提醒仍需自己寻找任务；未安排日期、其他日期任务尤其难找。任务显示已设置提醒，但用户可能不知道通知或对应渠道被关闭。
- **推荐修改**：单个任务提醒进入对应详情；多个同时到期事项可进入对应汇总列表。由现有提醒计划提供命中的事项，打开时核验账号与任务状态。设置提醒时解释通知与准时提醒能力，拒绝后仍保存任务，并明确说明当前限制；锁屏继续保护敏感内容。
- **原因**：通知应减少寻找成本，保存提醒时间与获得系统投递能力需要分别说明。
- **结构和流程影响**：目标 ID 可复用，不需要新增任务字段。需要扩展提醒事件、通知 PendingIntent 和 `MainActivity` 的目标处理；不需要把所有任务改成一条一条无节制推送。真正投递与后台限制必须在小米手机验证。
- **证据**：[提醒调度](../android/app/src/main/java/app/manman/teacher/reminders/ReminderScheduler.kt)、[提醒计划](../android/app/src/main/java/app/manman/teacher/reminders/ReminderPlan.kt)、[Intent 处理](../android/app/src/main/java/app/manman/teacher/MainActivity.kt)。

## C. 分页面优化方案

| 页面 | 推荐布局与交互 | 实施边界 |
| --- | --- | --- |
| 今天 | 保留大日期、星期、嫩芽菜单、通知、设置。固定“今日待办 / 待处理数 / 全部 / +”；下方主要是任务行。时间只在有具体时间时出现，不再重复当天日期。完成先原位划线，按确定后的规则进入已完成区。 | 今天不混入其他日期；增加入口不增加第二个同级加号。延续绿色与中性色和现有圆角。 |
| 快速添加 | 首轮沿用 `TaskEditorScreen`：标题自动聚焦；可见的今天或未安排 Chip；日期、时间、提醒按需展开；键盘提交与按钮保存；保存中只禁用本次提交。可后续增加保存并继续。 | 不要求先建清单；不自动联网解析输入。全屏与底部面板的取舍以后按大字号实测决定。 |
| 任务详情 | 标题与完成控件为主体；分别命名日期、具体时间、提醒；保留来自学校通知的入口；提供直接改期和更多菜单中的删除。备注仅在有内容或用户选择添加时展开。 | 现有模型没有备注。新增可选 JSON 字段时需更新 `WorkTask` 和 `RecordCodec.task`，测试旧数据默认值及旧客户端回写，不可假定旧客户端能保留未知字段。 |
| 计划 / 日历 | 当前没有独立日历。先在 `WorkScreen` 的全部待办中做日期导航与时间范围筛选，默认定位今天，未安排有明确入口；日期列表继续折叠。 | 同一份 `state.tasks`，不复制任务；跨日期通过编辑，保留同日期拖动。月历与拖动改期是 P2 备选，不预先扩展。 |
| 清单 / 筛选 | 先提供今天、未来日期、未安排、已完成、来自通知等查询视图，加简单搜索即可。条件 Chip 可清除，空筛选结果有清除筛选入口。 | 当前没有清单与标签。是否新增清单、标签、保存筛选器须验证实际组织需求，不为套用文档拆出四个底部 Tab。 |

自然语言日期、重复规则、子任务、看板和小组件列为 P2 候选；不能把缺少这些能力本身列为当前缺陷。语义不确定的日期必须让用户确认；若将来使用联网 AI，继续执行用户逐次确认发送的规则。

## D. 交互与异常状态补充

以下表格中的建议同样为待实施项。视图和事件处理通常不需增加任务字段；涉及持久草稿、备注或新日期语义时另行设计兼容。

| 场景 / 优先级 | 当前情况、影响 | 推荐行为与原因 |
| --- | --- | --- |
| 完成 · P1 | 已有复选框、划线、可取消完成；今日数仍包括完成项。 | 立即有视觉与轻触反馈，本机成功后确认状态；保持原任务 ID 和顺序。已完成去向有明确规则，失败能恢复并说明。 |
| 删除 · P0 | 确认后软删，暂无用户恢复。 | 确认与撤销分别覆盖预防和恢复；撤销可在已同步后提交新的恢复操作，不能只让屏幕看起来恢复。 |
| 改期 · P1 | 需要进入完整编辑，未提供改期撤销；提醒独立保存。 | 提供今天、明天、选日期、未安排等快捷项；改期后显示新位置。提醒跟随移动还是保留必须可见并确认，不能静默挪动。 |
| 拖动 · P1 | 同日期限制、稳定 key 和 48dp 拖动柄已具备；手柄只有说明，没有项目侧上移/下移等价操作。 | 沿用现有拖动组件，显示拖起/落点；补充菜单和 TalkBack 上移/下移。保持同日边界并支持恢复排序。 |
| 返回 · P1 | 未保存确认已有；页面由枚举切换，尚无按页面保留的 `SaveableStateHolder`。 | 保存列表滚动锚点、展开日期和筛选，再返回原位置；已被删除的目标给说明与返回入口。无需首轮更换导航框架。 |
| 离线 · P1 | 任务先保存本地并排队同步，方向正确。 | 已登录且凭证可本机恢复时，离线继续增改、完成、删除和撤销；状态条说明尚未同步。首次登录与账号验证仍需网络。 |
| 同步失败 / 冲突 · P1 | 设置页有重试、两版核对；首页只显示待同步数量或冲突数量。 | 用已有 `syncPhase` 区分等待、正在同步、需要登录与冲突，提供对应动作。保留两版，不把未上传说成未保存。 |
| 全局忙碌 · P1 | `busy` 同时服务本机写入和通知 AI 等耗时操作；任务控件依据它禁用。手动同步本身并未设置该标志。 | 按操作拆开忙碌状态，只防重复提交受影响事项；网络识别不应锁住其他本地任务。避免把此问题误写成同步必然阻塞保存。 |
| 本机写入失败 · P1 | 通用异常会给“检查网络或稍后重试”，即便失败来自本机保存。 | 明确区分未保存、本机已保存未同步、验证失败。未保存时保留编辑内容，给重试；保存成功前不提前关闭输入页。 |
| 空状态 · P1 | 今天为空时主要是一句提示；本机读取尚无独立 ready 状态。 | 区分本机尚未读完、真的无任务、今天全部完成、筛选无结果；分别给等待、添加、查看已完成、清除筛选。避免短暂空列表误导。 |
| 加载状态 · P1 | 有启动恢复进度和课程识别进度，不能据此声称任务录入依赖网络。 | 本机内容优先；只显示实际阶段。任务保存、云同步、AI 识别分别反馈，AI 完成不等于任务已正式保存。 |
| 权限拒绝 · P1 | 设置页已有通知与准时提醒入口，但录入提醒时解释不足。 | 先保存任务；就地提示通知、渠道或准时能力的限制，提供系统设置入口。返回应用时重新检查，避免反复强制申请。 |
| 大字号 / 读屏 · P1 | 有字号选项、图标描述和部分 200% 测试，不代表整条链路已经通过 TalkBack。 | 完成、打开、改期、删除和排序均能用读屏执行；日期按钮大字重排，标题可增高；焦点返回原操作处，状态用文字辅助表达。 |
| 视觉与触感 · P2 | 已有统一绿色和中性层级，且用户明确希望操作有清脆反馈。 | 保留当前品牌与触感方向。错误用明确文字和动作区分，不能只靠颜色。可增加触感减弱/关闭选项，遵循系统设置；不要根据通用指南直接取消此前确认的反馈。 |

减少动效后依然须看得出状态改变。触控区域至少 48dp，普通文字对比度至少 4.5:1，大字至少 3:1；这些是验收目标，本轮没有完成全部像素组合、设备及读屏测量。

## E. 分阶段实施顺序

## G. 需要补充的信息

不影响上述代码风险诊断，但会影响下一步交互与字段设计的决策如下：

1. **日期的业务含义**：现在一个日期同时决定任务在哪一天展示。是否保持这一规则，还是要分别记录“计划哪天做”和“最晚何时完成”？未确认前保留当前单日期语义。
2. **已完成项的去向**：当天始终留在原位，还是稳定反馈后放入可折叠已完成区？未确认前保留现有勾选划线行为。
3. **无日期通知任务的默认位置**：保持未安排并明确提示去向，还是新建时默认今天？不能自行给学校通知猜日期。
4. **真实使用与验证条件**：普通一天约多少条任务、最常用的录入来源，以及小米 12S 的 Android / HyperOS 版本。现阶段无需真实学生资料；后续可用虚构或脱敏任务验证。

最近删除的长期保留周期、重复任务、子任务和自定义清单可以在核心链路可靠后再确认。
